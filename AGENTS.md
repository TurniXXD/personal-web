# Project instructions

## Repository scope

- This is a pnpm monorepo with two independently deployed Next.js applications:
  - `apps/web`: the commercial site at `vantuch.dev`.
  - `apps/portfolio`: the interactive portfolio at `portfolio.vantuch.dev`.
  - `packages/ui`: assets and genuinely shared UI used by both applications.
- Use Node.js 22 or newer and the pinned `pnpm@11.6.0`. Do not use npm or Yarn in this repository.
- Preserve the separation between the two applications. A change for `apps/web` must not alter the portfolio unless the shared contract actually changes.
- Read the nearest `AGENTS.md` before editing. The block in `apps/web/AGENTS.md` is generated by Next.js and must remain intact.

## Source organization

- Keep route files thin. App Router pages should validate route parameters, load localized content and metadata, compose domain components, and little else.
- Organize components by feature or page section under `apps/web/components/<domain>`:
  - `components/ui`: shadcn-style primitives.
  - `components/shared`: small cross-feature components with proven reuse.
  - `components/home`, `components/services`, `components/contact`, and similar folders: domain-owned composition.
- Organize non-UI code by domain under `apps/web/lib/<domain>`. Provider clients belong in `lib/integrations`, observability in `lib/observability`, SEO in `lib/seo`, and route/slug definitions in `lib/site`.
- Keep localized content under `apps/web/messages` and mirror the feature structure. Use descriptive filenames such as `documents-reporting-and-monitoring.ts`, never numbered names such as `examples1.ts`.
- Use kebab-case filenames. React component and type names use PascalCase; functions and variables use camelCase; constants shared as enumerations use descriptive uppercase names.
- Do not place new feature files directly in `components`, `lib`, or `messages` when a domain folder exists or would make ownership clearer.
- Promote code to `shared` or `packages/ui` only after it has real consumers in multiple domains or applications. Do not create speculative abstractions.

## Component architecture

- Prefer Server Components. Add `"use client"` only to the smallest leaf that needs state, effects, browser APIs, pointer/scroll input, or a client-only Radix primitive.
- Never turn an entire route or large page composition into a Client Component to support one interactive child.
- Reuse the primitives in `apps/web/components/ui` before creating another button, card, menu, dialog, popover, or form-control abstraction.
- For new accessible interactive primitives, use this order:
  1. Existing project shadcn component.
  2. A shadcn component adapted to the project theme.
  3. A Radix primitive with Tailwind styling.
  4. A custom implementation only when neither shadcn nor Radix models the interaction.
- Radix owns interaction behavior such as focus management, keyboard navigation, dismissal, portals, and ARIA state. Style its `data-state`, `data-side`, `data-disabled`, and related attributes rather than recreating that behavior.
- Use Lucide icons by default. Decorative icons must have `aria-hidden="true"`; icon-only controls need an accessible name.
- Use semantic elements: links navigate, buttons perform actions, headings preserve hierarchy, and form controls have labels and useful autocomplete attributes.
- Repeated card families must share a primitive and interaction model. Avoid bespoke markup, unexplained empty footer space, or different hover timing for each card.

### Component example

```tsx
import Link from "next/link";
import { Button } from "@/components/ui/button";

type ContactActionProps = {
  href: string;
  label: string;
};

export function ContactAction({ href, label }: ContactActionProps) {
  return (
    <Button asChild variant="default">
      <Link href={href}>{label}</Link>
    </Button>
  );
}
```

Do not build the same element from a raw `<button>` plus duplicated focus, disabled, color, and spacing classes.

## Tailwind, shadcn, Radix, and CSS

- Tailwind CSS v4 is the default styling system. Use utilities for layout, spacing, sizing, typography, colors, borders, radii, shadows, responsive behavior, and ordinary hover/focus/open states.
- shadcn-style components are the default UI layer and Radix is the default behavior layer. Keep project primitives in `components/ui` composable through `className`, `data-slot`, `asChild`, CVA variants, and `cn`.
- Use semantic Tailwind theme variables from `apps/web/app/globals.css`. When a value repeats or represents a design decision, add a semantic token under `@theme inline` instead of repeating arbitrary values.
- Prefer names that describe purpose, such as `border-card`, `ink-muted`, `surface-soft`, `radius-card`, and `shadow-card`; do not name tokens after a single page or raw color.
- One-off geometry may use an arbitrary Tailwind value. Repeated colors, font sizes, radii, shadows, spacing, transition timing, and breakpoints must become semantic defaults or shared variants.
- Use CVA for a component with meaningful variants. Do not concatenate large conditional class strings in every consumer.
- Use `cn` for class composition. Do not introduce another class-merging utility.
- CSS Modules are reserved for styles that are genuinely clearer in CSS:
  - complex keyframes or multi-element animation choreography;
  - pseudo-element artwork;
  - masks, procedural gradients, orbit paths, or visual illustrations;
  - state shared across many visual descendants;
  - runtime CSS custom properties used by pointer or scroll animation.
- Keep an allowed CSS Module beside its component. Its component still owns ordinary layout, spacing, typography, borders, and responsive rules in Tailwind.
- Do not create a CSS Module for a normal card, grid, section, button, or breakpoint.
- `apps/web/app/styles/*.css` is a legacy migration surface. Do not add new feature selectors there. When touching an existing selector, move ordinary declarations into the owning component's Tailwind classes and leave only global foundations or complex shared motion that cannot be expressed clearly as utilities.
- `globals.css` should contain the Tailwind import, semantic theme tokens, global reset/foundation rules, and explicitly documented legacy imports. It is not a destination for page-specific CSS.
- Do not use inline `style` for static presentation. It is acceptable only for runtime values such as a measured coordinate or typed CSS custom property.

### Styling example

Prefer semantic utilities:

```tsx
<article className="rounded-card border border-border-card bg-card p-6 text-card-foreground shadow-card transition-colors hover:border-primary" />
```

Avoid repeated raw values:

```tsx
<article className="rounded-[1.5rem] border border-[#dce2fa] bg-[#fff] p-[24px] shadow-[0_24px_64px_rgba(36,46,94,0.12)]" />
```

For a unique animated visual, split responsibilities:

```tsx
<div
  className={cn("relative grid size-full place-items-center", styles.orbit)}
/>
```

```css
/* The module owns only the artwork and motion. */
.orbit::before {
  animation: orbit 14s linear infinite;
  offset-path: circle(46%);
}
```

## Visual and interaction rules

### Hero composition

- Never place decorative pipeline lines, connector tracks, or square-node dividers in or immediately after a hero section.
- Keep heroes focused on the headline, supporting copy, actions, and one relevant visual.
- Service heroes may have unique artwork and animation, but the artwork must explain the service and remain subordinate to the content.
- Decorative motifs that do not belong to the hero may appear between later content sections.

### Hover and focus motion

- Never move an element upward on hover or focus. This includes cards, buttons, links, icons, badges, and nested content.
- Do not use negative vertical translations, negative `top` changes, or equivalent upward motion in hover/focus states.
- Hover feedback may change color, border, shadow, opacity, subtle scale or rotation, or an intentional horizontal arrow position while keeping vertical layout fixed.
- Use a consistent short card transition. Long easing belongs to illustrative animation, not ordinary UI feedback.
- Hover and focus must communicate the same state. Never make essential information available only on hover.
- When touching an existing interaction, remove upward hover movement in the touched UI.

### Scroll, pointer, and animation behavior

- Reuse `ScrollReveal`, `ScrollAwareHeader`, and existing pointer-reactive visual helpers instead of creating parallel implementations.
- Scroll and pointer handlers must be passive where appropriate and batch visual updates with `requestAnimationFrame`. Avoid React state updates on every pointer or scroll event when CSS variables or refs suffice.
- Clamp pointer displacement and use smoothing for hero cards and decorative layers; cursor effects must not pull elements far from their composition.
- Every non-essential animation must honor `prefers-reduced-motion: reduce` and render a complete, readable static state.
- Animation must not cause layout shifts, obscure controls, block pointer input, or make content depend on JavaScript becoming active.
- Sticky navigation must reappear on upward scrolling and remain visible while its menu is open or focus is inside it.

## TypeScript and React code style

- TypeScript strict mode is the baseline. Do not introduce `any`, unchecked casts, or duplicate domain shapes to silence the compiler.
- Define every object parameter with a named type. Component props use `ComponentNameProps`; helper inputs use a descriptive name such as `CreateServiceSchemaParams`.
- Never declare object types inline in a function parameter list.
- Keep types near their domain owner and export them only when another module consumes them.
- Prefer readonly arrays and literal unions for finite content and route sets. Use `satisfies` when it preserves useful inference while checking a contract.
- Use early returns for invalid or unavailable states. Keep provider and parsing details out of React components.
- Use the `@/` alias for cross-folder imports inside `apps/web`; use relative imports only for colocated files such as a component and its CSS Module.
- Remove dead code and obsolete files when replacing an implementation. Do not leave numbered backups or commented-out alternatives.
- Comments explain constraints and non-obvious decisions, not what a line of code already says.

### Parameter typing example

```ts
type ClampParams = {
  value: number;
  min: number;
  max: number;
};

const clamp = ({ value, min, max }: ClampParams) =>
  Math.min(Math.max(value, min), max);
```

Do not write `const clamp = ({ value, min, max }: { value: number; min: number; max: number }) => ...`.

## Localization, routes, and static generation

- Czech and English are equal product variants. Whenever user-visible copy changes, update both locales in the same change even when the request mentions only one language.
- Store user-visible copy in the locale message catalogs and read it through `next-intl`. Do not add language conditionals or literal UI sentences inside components.
- Brand names, protocol identifiers, schema.org keys, and genuinely language-neutral labels may remain constants.
- Keep route segments and slugs in shared semantic constants in `lib/site/routes.ts`. Do not compare or assemble route slugs from ad-hoc string literals in components.
- Localized slugs must use the shared locale mapping. The page generator, navigation, canonical URLs, alternate-language links, and sitemap must consume the same source.
- Public content pages must remain statically generated:
  - enumerate locale/slug combinations with `generateStaticParams`;
  - call `setRequestLocale(locale)` before localized rendering;
  - keep request-specific data, cookies, headers, and mutations in API routes or client leaves;
  - do not opt a public page into dynamic rendering for convenience.
- Generate page metadata from the same localized copy as the page. Preserve canonical and alternate-language URLs.
- Keep Google structured data builders in `lib/seo/structured-data.ts` and render them through `StructuredDataScript`. Human-readable schema values come from localized content; schema identifiers and stable organization constants may remain in code.
- Whenever a public page is added, removed, renamed, hidden, or changes its canonical route, update `apps/web/app/sitemap.ts` for Czech and English in the same change.
- Keep `apps/web/app/robots.ts` aligned with public route visibility and preserve the canonical sitemap URL.

## Accessibility and responsive behavior

- Preserve visible keyboard focus. Use the semantic `ring`/`primary` tokens rather than removing outlines.
- Interactive controls must work with keyboard, touch, and pointer input. Radix menus must retain their built-in keyboard and focus behavior.
- Maintain readable contrast in default, hover, focus, open, disabled, and dark-surface states.
- Use mobile-first Tailwind utilities and verify narrow phone, tablet, desktop, and WebKit behavior when layout or interaction changes.
- Do not hide required content on mobile merely to make a layout fit. Reflow or simplify the composition.
- Avoid fixed heights for copy-heavy cards and translated text. Prefer intrinsic sizing and `min-*` constraints only when needed.
- Images use `next/image` when appropriate, include meaningful alt text, and declare realistic responsive `sizes`.

## API routes, integrations, and observability

- Treat every API payload as untrusted. Validate and normalize it in a domain module before calling providers.
- Keep Turnstile verification, honeypots, and rate limiting on public form endpoints. Never trust referral identity, source paths, or attribution supplied directly by a browser.
- Provider clients belong in `lib/integrations`; route handlers orchestrate them and translate failures into the shared API response contract.
- Use `apiErrorResponse` and `sentryLogger` for handled API failures. Do not add isolated `console.error` reporting paths.
- Sentry diagnostics may contain operational metadata only. Never attach form bodies, contact data, cookies, authorization headers, API keys, tokens, or raw secrets.
- Redact provider response bodies and expose safe diagnostics as flat, named fields when they need to be visible in Sentry.
- External requests must have an explicit timeout, intentional cache behavior, and useful redacted error context.
- Secrets remain server-only and must never use a `NEXT_PUBLIC_` prefix. Public configuration is limited to values that are safe to ship to every browser.
- Preserve the CSP and security headers in `apps/web/next.config.ts`. Any new external script, frame, image, or connection requires the narrowest corresponding CSP change.
- Keep `.env` files out of Git. Example environment files contain placeholders only; dependency or deployment changes must update the documented environment contract.

## Testing and verification

- Add or update the closest test whenever behavior changes. Tests live with the owning application; commercial-site E2E coverage is in `apps/web/e2e`.
- Prefer stable behavior assertions, roles, labels, URLs, and `data-*` state over brittle DOM depth, generated class names, or pixel-perfect timing.
- UI changes should cover the relevant combination of:
  - keyboard and accessibility behavior;
  - mobile/WebKit layout;
  - reduced motion;
  - locale and localized route behavior;
  - navigation, card, or form interaction.
- Provider integration tests must use simulated fetchers and must not contact real production services.
- Run focused checks while iterating, then verify the affected application. At minimum for `apps/web` changes:

```sh
pnpm exec prettier --check <changed-files>
pnpm exec eslint <changed-files>
pnpm --filter @vantuch/web typecheck
pnpm exec playwright test apps/web/e2e/<relevant-spec>.spec.ts
git diff --check
```

- Before handing off a broad refactor or dependency/configuration change, run the relevant root checks:

```sh
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test --runInBand
pnpm build
pnpm test:e2e
```

- A production web build validates required environment variables before compilation. Use `VALIDATE_PRODUCTION_ENV=true pnpm --filter @vantuch/web validate:production-env` when intentionally checking the production environment contract.
- Do not commit `.next`, `.next-dev`, `test-results`, logs, local environment files, or other generated output.

## CI/CD and dependencies

- GitHub Actions in `.github/workflows/ci.yml` is the source of truth for merge checks. Keep local scripts and CI commands aligned.
- CI uses Node.js 22, pnpm 11.6.0, a frozen lockfile, lint, Prettier, strict type checking, unit tests, production builds, and Chromium/WebKit Playwright tests.
- When adding or updating a dependency, change the correct workspace package and commit the root `pnpm-lock.yaml`. Do not duplicate a dependency in multiple packages without need.
- Keep the development server on `.next-dev` and production/E2E builds on `.next` as configured. Use the dev server for visual iteration and production builds for final verification.
- The repository deploys as two Vercel projects with `apps/web` and `apps/portfolio` as separate Root Directories. Preserve access to `packages/ui` through the monorepo setting for source files outside the Root Directory.
- Do not change domains, Vercel Root Directories, production environment variables, DNS, or provider configuration unless the task explicitly authorizes that external change.
- New required environment variables must be added consistently to validation, documentation, and every affected deployment environment before relying on them.
- Keep server secrets out of build output, client bundles, test artifacts, Sentry context, and command output.

## Change discipline

- Preserve unrelated user changes and avoid broad formatting churn outside the task.
- When touching legacy code, improve the touched boundary toward these rules instead of cloning the legacy pattern.
- A refactor is complete only when imports, tests, content files, sitemap/SEO sources, and obsolete files are updated together.
- Prefer a small coherent diff with an explicit owner over another compatibility layer or duplicate implementation.
